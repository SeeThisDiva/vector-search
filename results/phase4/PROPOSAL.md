### 1.3 Key Architectural Finding from the Pilot

1. **Strict Monotonicity**: Recall increases monotonically from $0.82103$ ($\text{efSearch}=10$) to $0.99702$ ($\text{efSearch}=600$).
2. **Diminishing Returns at High `efSearch`**:
   - Sweeping $\text{efSearch} \in \{300, 400, 600\}$ consumes **$58.4\%$** ($101.3\text{ s}$ out of $173.5\text{ s}$) of the total sweep time.
   - However, the recall delta across that entire top tier is just $+0.00057$ ($0.99645 \to 0.99702$).
   - At $\text{efSearch}=400$, recall is already $0.99700$ (99.70%), virtually identical to $\text{efSearch}=600$. This observation informs our optional fast-sweep optimization under Gate G2.

## 2. Proposed Grid Specification & Cardinality

The wide parameter sweep is defined declaratively in [`results/phase4/grid_100k.grid`](./grid_100k.grid):

```ini
# Phase 4 Wide Parameter Sweep Grid (100k SIFT1M prefix)
# Cartesian product of M x efConstruction filtered by efConstruction >= M (23 configs)
scale = 100000
k = 10
sweep_runs = 3
seed = 42
ef_search = 10, 20, 30, 40, 50, 70, 100, 150, 200, 300, 400, 600
m = 8, 12, 16, 24, 32, 48
ef_construction = 40, 100, 200, 400
```

### 2.1 Grid Filtering & Cardinality: 23 vs 24 Configurations

- Standard Cartesian Product: $6 \text{ values of } M \times 4 \text{ values of } \text{efConstruction} = 24 \text{ combinations}$.
- Invariant Condition: per HNSW design principles, construction beam width must be at least the layer degree limit ($\text{efConstruction} \ge M$).
- At $M=48$ and $\text{efConstruction}=40$, we have $40 < 48$, which violates this constraint. `Phase4GridSpec::parse_str` automatically filters out this invalid pair, yielding **23 strictly valid Cartesian configurations**.
- **Alternative (24 configs)**: If an even 24-point grid is preferred, an explicit configuration line `config = m:48, ef_construction:48` can be added as the 24th point.

## 3. Empirical Time-Budget Extrapolation

### 3.1 Scaling Model Grounded in Phase 3.5 Profiling

Phase 3.5 flamegraph profiling established that insertion time is dominated by:
1. `search_layer` (beam search at layer 0): $52.27\%$ of build time, scaling with $\mathcal{O}(\text{efConstruction} \cdot M^{\alpha_1})$.
2. `shrink` (heuristic neighbor selection): $31.95\%$ of build time, scaling with $\mathcal{O}(M^2)$.
3. Forward heuristic pass: $15.49\%$ of build time.

We model build and query sweep scaling from the pilot baseline ($T_{\text{build},0} = 26.066\text{ s}$, $T_{\text{sweep},0} = 173.493\text{ s}$):

$$\begin{aligned}
T_{\text{build}}(M, \text{efC}) &= T_{\text{build},0} \cdot \left(\frac{M}{16}\right)^\alpha \cdot \left(\frac{\text{efC}}{100}\right)^\beta \\
T_{\text{sweep}}(M) &= T_{\text{sweep},0} \cdot \left(\frac{M}{16}\right)^\gamma
\end{aligned}$$

- **Expected Parameters**: $\alpha = 0.65$, $\beta = 0.85$, $\gamma = 0.45$ (reflects flat-array cache locality and vectorized distance kernels).
- **Worst-Case Parameters**: $\alpha = 0.90$, $\beta = 1.00$, $\gamma = 0.65$ (conservative upper bound assuming branch mispredictions at large $M$).

## 4. 1M Final Confirmation Budget (3 to 4 Pareto-Optimal Configurations)

### 4.1 Scaling from Phase 3.5 1M Measurement

The 1M baseline was rigorously measured on clean commit `366f185` ([`results/phase3_5/final_1m_report.json`](../phase3_5/final_1m_report.json)):
- $M=16, \text{efConstruction}=100$ build: **$493.776\text{ s}$ ($8.23\text{ min}$)**.
- Query latency scales by $\approx 1.85\times$ from 100k to 1M (due to $\log N$ graph depth and increased L3 cache misses).
- 5 timed repetitions + 1 untimed warmup = 6 passes ($1.5\times$ pass count vs 100k).
- Expected 12-point sweep time at 1M ($M=16$, 5 reps): $43.373\text{ s} \cdot 1.85 \cdot 6 \approx 481.4\text{ s}$ ($8.02\text{ min}$).

## 6. Execution Safety & Resumability Protocol

1. **Clean Commit Invariant**: All benchmark runs are pinned to a clean Git commit (`git_dirty: false`). Reports generated on dirty trees are rejected and will not resume cleanly.
2. **Crash & Sleep Resumability**: `can_resume_existing_report` checks per-index JSON existence, matching `git_commit`, `scale_vectors`, `num_query`, `k`, `sweep_runs`, $M$, $\text{efConstruction}$, and the complete `efSearch` list. If a run is interrupted, previously completed configurations are skipped in milliseconds.
3. **Core Affinity**: Single-thread benchmarking is pinned to P-core affinity mask `0x0004` to avoid Windows thread migration between Performance and Efficient cores.
